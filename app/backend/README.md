# Backend — Flash Sale

NestJS + Fastify + TypeScript. Currently boilerplate plus the persistence layer:
one dummy endpoint, no real purchase logic yet, but Postgres (via Drizzle) and
Redis are wired up and reachable.

## Stack

- **NestJS** on the **Fastify** adapter (`@nestjs/platform-fastify`), not Express.
- **Swagger** (`@nestjs/swagger`) served at `/docs`.
- **`@nestjs/config`** wrapped in a project `ConfigService` — typed getters instead
  of reading `process.env` directly. See `src/config/config.service.ts`.
- **Drizzle** as the query builder against **PostgreSQL** (via the `postgres` driver).
  No TypeORM-style Repository base class — `PurchaseRepository` is a plain
  `@Injectable()` wrapping an injected Drizzle client, per the root README's
  architecture section.
- **Redis** — not yet wired into application code; provisioned by docker-compose
  ahead of the atomic purchase decision logic that will use it (see root README).
- **Jest** (`.test.ts` suffix, not `.spec.ts`) — wired but no tests written yet.

## Structure

```
src/
  main.ts              Bootstraps Nest + Fastify, mounts Swagger, reads port from ConfigService.
  app.module.ts         Root module — imports ConfigModule, DatabaseModule, FlashSaleModule.
  common/error/
    await-to-error.ts   [err, result] tuple wrapper, used at the repository/persistence
                         boundary instead of try/catch.
  config/
    config.module.ts    Global module wrapping @nestjs/config, resolves .env by file
                         location (not process.cwd()) so it works regardless of the
                         directory the process is launched from.
    config.service.ts   Typed getters: config.app().port, config.database().*.
    validate-env.ts     Throws at startup if a required env var is missing (skipped
                         when NODE_ENV=test).
  db/
    client.ts            createDrizzleClient() — a postgres-js connection + Drizzle wrapper.
    database.module.ts   Global module, provides DRIZZLE_CLIENT built from ConfigService.
    schema.ts             Re-exports every module's Drizzle table definitions.
    migrations/            Generated by `drizzle-kit generate`, committed to the repo.
  flash-sale/
    domain/flash-sale/          Business logic. flash-sale.service.ts currently returns
                                 a hardcoded dummy SaleStatus — not wired to the repository yet.
    application/rest/
      controller/                flash-sale.controller.ts — GET /v1/flash-sale/status.
      response/                  Swagger-documented response DTOs.
    infrastructure/repository/purchase/
      purchase.entity.ts          Drizzle schema for `purchases` — UNIQUE(sale_id, identifier).
      purchase.repository.ts      PurchaseRepository — findByIdentifier, count, insertIfNotExists.
    types/                       as const status/error code objects (see root README's
                                  naming conventions).
    flash-sale.module.ts
```

This layering (`domain` / `application` / `infrastructure` / `types` per module)
mirrors an internal NestJS boilerplate pattern, kept to the single module this
system needs — no CQRS, no extra modules for the sake of structure.

`PurchaseRepository` exists and is wired into `FlashSaleModule`'s providers, but
`FlashSaleService` does not call it yet — the dummy endpoint's response is still
hardcoded. Wiring the two together is the next step (the atomic purchase decision),
not part of this setup.

## Running

From the repo root, `npm run dev` starts backend and frontend together (see the
[root README](../../README.md)). To run just this app against local infrastructure:

```bash
npm install
cp .env.example .env
docker compose -f build/docker/docker-compose.yml up -d db redis
npm run db:migrate
npm run dev
```

Starts at `http://localhost:3000`. Swagger docs at `http://localhost:3000/docs`.

To run the backend itself inside Docker too (hot-reloading, source mounted from the
host):

```bash
docker compose -f build/docker/docker-compose.yml -f build/docker/docker-compose.override.yml up
```

## Configuration

Copy `.env.example` to `.env` before running — all variables below are required at
startup (validation is skipped when `NODE_ENV=test`).

| Variable | Required | Purpose |
|---|---|---|
| `PORT` | Yes | Port the Fastify server listens on. |
| `DB_HOST` | Yes | Postgres host. |
| `DB_PORT` | Yes | Postgres port. |
| `DB_NAME` | Yes | Postgres database name. |
| `DB_USERNAME` | Yes | Postgres user. |
| `DB_PASSWORD` | Yes | Postgres password. |

## Database

```bash
npm run db:generate   # generate a migration from src/db/schema.ts after a schema change
npm run db:migrate    # apply pending migrations to the configured database
npm run db:studio     # browse the database with Drizzle Studio
```

Drizzle schema is the source of truth for the database shape — never hand-edit the
database. Migrations are generated files, committed under `src/db/migrations/`.

## API reference

### `GET /v1/flash-sale/status`

Returns the current sale status. **Dummy response** — always returns the same
hardcoded body regardless of any real sale window or stock state.

```json
{
  "status": "upcoming",
  "productName": "Limited Edition Product",
  "productDescription": "Dummy response — not wired to real state yet.",
  "startsAt": "2026-01-01T00:00:00.000Z",
  "endsAt": "2026-01-01T00:00:00.000Z",
  "stockRemaining": 0,
  "totalStock": 0
}
```

Two more endpoints are planned per the brief (attempt purchase, check own result)
but not implemented yet.
