# Backend — Flash Sale

NestJS + Fastify + TypeScript. All three brief endpoints are implemented and backed
by real state: the atomic purchase decision runs in Redis (Lua script), Postgres is
the durable source of truth, and both are exercised end-to-end by automated tests
(unit + integration against real infrastructure).

## Stack

- **NestJS** on the **Fastify** adapter (`@nestjs/platform-fastify`), not Express.
- **Swagger** (`@nestjs/swagger`) served at `/docs`.
- **`@nestjs/config`** wrapped in a project `ConfigService` — typed getters instead
  of reading `process.env` directly (the one exception is `main.ts`'s `FastifyAdapter`
  construction, which resolves `ConfigService` from a standalone `ConfigModule`
  application context before the main app's DI container exists — see the comment there).
  See `src/config/config.service.ts`.
- **Drizzle** as the query builder against **PostgreSQL** (via the `postgres` driver,
  connection pool size configurable — `DB_POOL_MAX`, see Configuration below).
  No TypeORM-style Repository base class — `PurchaseRepository`/`SaleRepository` are
  plain `@Injectable()` classes wrapping an injected Drizzle client, per the root
  README's architecture section.
- **Redis** (`ioredis`) — the atomic purchase decision (`purchase.lua`, executed via
  `PurchaseGateway`) runs here. See root README's Decision 1.
- **Jest** (`.test.ts` suffix, not `.spec.ts`) — unit suite (mocked infra) and a
  separate integration suite (real Postgres + Redis), run independently.

## Structure

```
src/
  main.ts              Bootstraps Nest + Fastify (keep-alive/connection timeouts read
                        from ConfigService via a standalone app context), mounts
                        Swagger, enables CORS, listens on ConfigService's port.
  app.module.ts         Root module — imports ConfigModule, DatabaseModule,
                         FlashSaleModule, RedisModule.
  common/error/
    await-to-error.ts   [err, result] tuple wrapper, used at the repository/persistence
                         boundary instead of try/catch.
  config/
    config.module.ts    Global module wrapping @nestjs/config, resolves .env by file
                         location (not process.cwd()) so it works regardless of the
                         directory the process is launched from.
    config.service.ts   Typed getters: app() (port, HTTP timeouts), database()
                         (connection + pool size), redis().
    validate-env.ts     Throws at startup if a required env var is missing (skipped
                         when NODE_ENV=test).
  db/
    client.ts            createDrizzleClient() — a postgres-js connection (pool size
                          from ConfigService) + Drizzle wrapper.
    database.module.ts   Global module, provides DRIZZLE_CLIENT built from ConfigService.
    schema.ts             Re-exports every module's Drizzle table definitions (sales, purchases).
    migrations/            Generated by `drizzle-kit generate`, committed to the repo.
                           0001 also seeds the one `sales` row (id: "default").
  redis/
    redis.client.ts       createRedisClient() — thin ioredis wrapper.
    redis.module.ts       Global module, provides REDIS_CLIENT built from ConfigService.
  flash-sale/
    domain/flash-sale/
      flash-sale.service.ts    The atomic purchase decision + window logic — orchestrates
                                SaleRepository, PurchaseRepository, PurchaseGateway.
      flash-sale.interface.ts  Service-level option/return shapes.
      flash-sale.test.ts       Unit tests — all three dependencies mocked with jest.fn().
    application/rest/
      controller/
        flash-sale.controller.ts        The three endpoints from the brief.
        flash-sale.integration.test.ts  Integration tests — real Nest app, real Postgres/Redis.
      request/attempt-purchase.request.ts   class-validator DTO for the purchase body.
      response/
        get-sale-status.response.ts     Swagger-documented status response shape.
        attempt-purchase.response.ts    Swagger-documented purchase/check response shape.
    infrastructure/
      redis/
        purchase.lua              The atomic Lua script: window + dedup + stock, one round trip.
        purchase-gateway.ts        PurchaseGateway — bootstraps Redis stock from Postgres on
                                    first use, then EVALSHAs the script.
      repository/
        purchase/purchase.entity.ts     Drizzle schema for `purchases` — UNIQUE(sale_id, identifier).
        purchase/purchase.repository.ts PurchaseRepository — findByIdentifier, count, insertIfNotExists.
        sale/sale.entity.ts             Drizzle schema for `sales` — static per-sale config.
        sale/sale.repository.ts         SaleRepository — findById.
    types/
      purchase.ts        PurchaseErrorCode, LuaOutcome, PurchaseErrorHttpStatus (as const
                          objects — see root README's naming conventions).
      sale-status.ts      SaleWindowStatus.
    flash-sale.module.ts
```

This layering (`domain` / `application` / `infrastructure` / `types` per module)
mirrors an internal NestJS boilerplate pattern, kept to the single module this
system needs — no CQRS, no extra modules for the sake of structure.

## Running

From the repo root, `npm run dev` starts backend and frontend together (see the
[root README](../../README.md)). To run just this app against local infrastructure:

```bash
npm install
cp .env.example .env
docker compose -f build/docker/docker-compose.yml up -d db redis
npm run db:migrate
npm run dev
```

Starts at `http://localhost:3000`. Swagger docs at `http://localhost:3000/docs`.

To run the backend itself inside Docker too (hot-reloading, source mounted from the
host):

```bash
docker compose -f build/docker/docker-compose.yml -f build/docker/docker-compose.override.yml up
```

Or from the repo root: `npm run docker:up:backend` (dev) / `npm run docker:up:backend:prod`
(production image, built by `build/docker/dockerfile`'s `runner` stage).

## Configuration

Copy `.env.example` to `.env` before running.

| Variable | Required | Default | Purpose |
|---|---|---|---|
| `PORT` | Yes | — | Port the Fastify server listens on. |
| `HTTP_KEEP_ALIVE_TIMEOUT_MS` | No | `30000` | Fastify/Node HTTP keep-alive timeout. Raised from Node's default after CI's oversell test (30 concurrent requests) intermittently hit `ECONNRESET` under a throttled runner. |
| `HTTP_CONNECTION_TIMEOUT_MS` | No | `30000` | Fastify/Node HTTP connection timeout. Same reasoning as above. |
| `DB_HOST` | Yes | — | Postgres host. |
| `DB_PORT` | Yes | — | Postgres port. |
| `DB_NAME` | Yes | — | Postgres database name. |
| `DB_USERNAME` | Yes | — | Postgres user. |
| `DB_PASSWORD` | Yes | — | Postgres password. |
| `DB_POOL_MAX` | No | `10` | postgres-js connection pool size. Raised (e.g. to `50`) where concurrent purchase load needs more headroom than one connection per in-flight request — see the oversell test note above; the pool was the actual bottleneck, not the HTTP layer, once diagnosed. |
| `REDIS_HOST` | Yes | — | Redis host. |
| `REDIS_PORT` | Yes | — | Redis port. |

`validate-env.ts` fails startup fast if any `Yes`-required variable above is missing
(skipped when `NODE_ENV=test`, since CI supplies these as real env vars instead of a
`.env` file).

## Database

```bash
npm run db:generate   # generate a migration from src/db/schema.ts after a schema change
npm run db:migrate    # apply pending migrations to the configured database (also seeds
                       # the one `sales` row, id "default" — see migration 0001)
npm run db:studio     # browse the database with Drizzle Studio
```

Drizzle schema is the source of truth for the database shape — never hand-edit the
database. Migrations are generated files, committed under `src/db/migrations/`.

## API reference

See the [root README's API reference](../../README.md#api-reference) for full
request/response shapes and the error taxonomy table — this section just lists the
routes. Swagger docs (interactive, with schemas) are served at `/docs` once the
backend is running.

| Endpoint | Purpose |
|---|---|
| `GET /v1/flash-sale/:saleId/status` | Sale status (upcoming/active/ended), stock remaining |
| `POST /v1/flash-sale/:saleId/purchase` | Attempt a purchase — body: `{ "identifier": string }` |
| `GET /v1/flash-sale/:saleId/purchase/:identifier` | Check whether this identifier has secured an item |

`:saleId` is currently always `"default"` — the one seeded row.

## Testing

```bash
npm test              # unit — fast, no infrastructure, all deps mocked
npm run test:coverage # unit, with coverage report
npm run test:integration  # requires `docker compose ... up -d db redis` + a migrated DB
npm run test:stress    # requires the above, plus the server itself running (npm run dev)

or

STRESS_TEST_STOCK=50 STRESS_TEST_CONCURRENCY=1000 STRESS_TEST_ITERATIONS=10 STRESS_TEST_DUPLICATE_CONCURRENCY=100 npm run test:stress

```

Unit tests (`flash-sale.test.ts`) mock `SaleRepository`/`PurchaseRepository`/
`PurchaseGateway` with `jest.fn()` — fast, no infra needed. Integration tests
(`flash-sale.integration.test.ts`) boot the real Nest app and drive it over HTTP with
`supertest` against real Postgres and Redis, run with `--runInBand` (not for
parallelism reasons — each test seeds and cleans up its own `sales`/`purchases` rows,
sequencing just avoids cross-test interference). Deliberately not mocking Redis here:
the whole point of this layer is proving the atomic decision holds against the real
thing. The stress test (`src/flash-sale/stress-test/run-stress-test.ts`) drives the
real running server over plain HTTP at much higher concurrency (config via
`STRESS_TEST_STOCK`/`STRESS_TEST_CONCURRENCY`/`STRESS_TEST_ITERATIONS`/
`STRESS_TEST_DUPLICATE_CONCURRENCY` env vars) and asserts the same oversell/duplicate-
user/boundary invariants against Postgres and Redis afterward, repeated automatically.
See the root README's Testing and Stress test results sections for what each suite
covers in detail and the actual numbers from the last run.
